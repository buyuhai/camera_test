# Design

## Context

当前实现只处理单张图片：`MainWindow._open_image` 通过 `load_image` 读取图片，`DetectThread` 在后台调用 `detect_circles`，结果经 `render_overlay` 叠加后显示在 `QLabel`。参数模型、检测算法和图片导出已经由归档变更验证，基线规格见 `openspec/specs/{image-io,circle-detection,detection-workbench}/spec.md`。

视频模式需要在不改变图片路径的前提下，持续解码并检测多帧；因此复用检测与渲染函数，新增独立的视频读取与播放线程。

## Goals / Non-Goals

**Goals:**

- 在现有单窗口内增加视频打开、播放/暂停、停止和逐帧检测。
- 复用 `HoughParams`、`detect_circles`、`render_overlay`，避免复制检测逻辑。
- 保证视频线程可控退出，窗口关闭时不残留线程或解码器。
- 中文路径、无法解码文件等错误路径与图片模式保持一致的提示方式。

**Non-Goals:**

- 不实现音频播放、跨帧目标跟踪、跳转定位、逐帧单步或导出标注视频。
- 不改变图片模式的检测参数、算法、叠加样式和导出行为。
- 不在本次变更中引入新的第三方依赖或自建解码器。

## Decisions

- **视频读取使用 `cv2.VideoCapture`。** 现有环境已依赖 OpenCV 4.6，其 FFmpeg 后端可覆盖 MP4/AVI/MOV；不需要新增依赖。读取模块放在 `hough_gui/core/`，不依赖 Qt，便于用合成视频单测。
- **视频检测使用独立 `QThread`。** 图片模式继续使用现有 `DetectThread`；视频模式新增 `VideoDetectThread`，循环执行「读帧 → 检测 → 叠加 → 发信号」。两个线程不共享可变检测状态。
- **只保留最新帧。** 解码/检测慢于视频帧率时允许跳帧，但预览必须显示最新完成的结果；不建立无界帧队列，避免内存增长。
- **参数按帧快照。** 主线程在启动一帧检测前读取当前参数并传给线程；参数变化只影响后续帧，不回算历史帧。
- **暂停与停止用线程内标志控制。** 暂停时线程等待，停止时设置退出标志并释放 `VideoCapture`；`closeEvent` 必须等待线程结束。
- **错误处理沿用现有模式。** 打开失败用 `QMessageBox.critical`，并保持当前图片/视频状态不变；不把 OpenCV 的静默失败当成空视频继续播放。
- **视频模式禁用「导出标注图」。** 本变更不定义视频导出格式与编码参数，避免把未确认的需求带进实现。

## Risks / Trade-offs

- **编解码器可用性依赖系统 OpenCV 构建。** 某些 MOV/AVI 编码可能无法解码；实现时需用实际样例验证，并在错误提示中说明文件无法解码，而不是崩溃。
- **检测速度可能低于视频帧率。** 允许跳帧会把「逐帧」变成「尽可能逐帧」；验收时应记录实际处理帧率，避免把跳帧误判为漏检。
- **中文路径在 `cv2.VideoCapture` 上的行为需要实测。** 图片路径已用 `np.fromfile` 规避；视频没有等价的内存读取入口，若实测失败，需要评估 `os.fsencode`/临时路径等方案，并把结论记录到验收记录。
- **线程退出是主要稳定性风险。** 暂停/停止/关窗三种路径都要覆盖，避免关闭窗口后线程仍在解码。
- **未确认的导出视频需求。** 如果需求方要求导出标注视频，会引入编码器选择、音轨处理和文件体积问题，建议作为独立变更，不塞进本次范围。

## Open Questions

- 视频播放是否需要音频？当前设计假定不需要。
- 是否需要视频导出（标注后的 MP4/AVI）？当前设计明确不做，留作后续独立变更。
- 是否需要拖动进度条或逐帧单步？当前设计只做播放/暂停/停止。
- 跳帧策略是否可接受？当前设计优先保证界面响应和最新结果，不保证每一帧都检测。
